# 开发者测试模式

[English](DeveloperTesting.md) · [目录架构](SignedCatalog.zh-CN.md)

在 Settings → 应用与服务 → **进入测试模式**，可以在投稿前测试自己的 GitHub Release 目录。测试模式保留原应用 ID，使用现有用户 Flatpak 安装。它不是独立的应用沙箱：测试包可能替换已安装应用，并使用原有数据。重要数据请先备份，安装、升级等回归建议在开发虚拟机中完成。

## 发布并选择测试版本

1. 使用原应用 ID 和 `stable` Flatpak 分支构建 bundle，把包和 schema 2 发行清单上传到自己的公开 GitHub 仓库。清单版本必须等于去掉 `v` 的标签，例如 `v1.2.0-rc.1` / `1.2.0-rc.1`。明确选中后支持已发布的 GitHub 预发行版；不支持草稿和私有仓库认证。
2. 参考 [appCatalog](https://github.com/NextKde/appCatalog) 准备独立的测试目录仓库。条目填写应用仓库、原 ID 和清单文件名。用自己的来源 ID 和递增序号生成目录，用自己的目录密钥签名。将 `catalog.json`、`catalog.json.sig` 上传到已发布的 GitHub Release，例如 `catalog-test-1`，可以标记为预发行。
3. 进入测试模式并打开**管理应用来源**。添加测试来源 ID、GitHub 仓库、导出的二进制 `.gpg` 公钥和完整指纹，明确确认信任。测试来源初始为空，不继承官方信任配置。
4. 在来源的**目录 Release**中选择已发布的标签，应用后刷新并验签。留空表示最新稳定版。选择旧目录不能绕过序号和有效期检查；需要独立的序号历史时，使用新的测试来源 ID，并同步修改、签发目录中的 `sourceId`。
5. 展开应用详情，通过**应用 Release**选择测试版本，再点击**检查更新**。列表显示最多 30 个近期已发布版本，也可输入旧版本的完整标签。安装或更新前，确认依赖计划及测试模式提示。
6. 发布更高版本的测试包，选择对应 Release 并重新检查，即可验证升级。降级或同版本替换测试需先卸载，测试模式不跳过版本检查。若现有安装属于其他来源，或不能通过所选开发者公钥验证，也需先卸载再安装测试版。

目录签名与包 SHA-256 仍然必需。开发者签名可选，但配置公钥后严格验证。下载仍限定在登记的 GitHub 仓库 Release 附件，不支持本地包路径、raw URL、任意服务器或安装脚本。

## 退出与恢复

**退出测试模式**仅恢复正常来源配置，不卸载应用、不恢复旧版本、不删除应用数据，也不把测试源迁移到正常配置。测试安装保留打开、卸载入口，正常更新器不会静默接管。需要恢复时，请自行卸载测试版，再安装正式版；正常卸载流程保留应用数据。

测试模式暂停定时更新检查和桌面更新通知，仍可手动刷新目录、检查单个应用或**检查全部更新**。来源错误、所选标签、已安装/可用版本和操作日志可用于排查问题。

## 状态与验收

模式按用户保存，重启 Settings 后保留，作用于 Settings、CLI、worker 和 updater 共用的后端。CLI 结果包含 `testMode`。测试来源保存在正常 `app-sources.json` 旁的 `app-sources-test.json`；目录缓存和更新状态使用 `app-catalog/test/`；测试计划使用 `flatpak-plans-test/`。实际 Flatpak 安装、应用数据和安装归属记录共用，记录中标记该次部署是否为测试安装。

切换模式或应用 Release 后，旧计划和缓存版本发现失效。共用的上下文锁阻止在目录刷新、安装清单查询和应用操作中途切换来源/模式；安装事务锁仍跨模式共用。更新器发现模式上下文变化后丢弃旧扫描结果。后台进程不会确认安装。

项目贡献者只能在虚拟机或 CI 构建与验证。覆盖正常/测试来源及序号分离、同 ID 安装记录、旧计划失效、签名/摘要失败、标签不符、预发行版本排序、暂停定时检查、手动检查及退出不卸载；再用虚拟机隔离夹具验收实际安装/升级/卸载和支持语言下的 Settings 界面。
